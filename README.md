# Android UI Automation

Python Appium + pytest scaffold for testing an existing Android APK on one or more Android devices.

## Setup

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
npm install -g appium@2
bash scripts/install_uiautomator2.sh
```

Allure raw results are generated by `allure-pytest`. The Allure CLI is installed globally through `allure-commandline` and is used to generate the HTML report automatically.
By default, the framework now manages Appium server processes for you and starts one local Appium service per selected device session.

## Device configuration

Configure devices in `config/appium.yaml` under `android.devices`. Parallel devices must use unique `appium_port`, `udid`, `system_port`, `chromedriver_port`, and `mjpeg_server_port` values.

If you do not pass `--device`, the runner uses every configured device from `config/appium.yaml` by default.

If Appium and your shell resolve different Android SDK installations, pin the SDK in `.env` with `ANDROID_ADB_PATH`, `ANDROID_SDK_ROOT`, and `ANDROID_HOME`. The runner and pytest fixtures will propagate those values to all `adb` checks and Appium session startup.

The `appium` section controls server lifecycle. With `manage_servers: true`, the pytest device session starts one Appium process per selected device, waits for each `http://host:port/status` endpoint to become healthy, and shuts that process down when the device session finishes. By default, stale local Appium processes on the same managed port are cleaned up automatically before startup. Set `manage_servers: false` only if you intentionally want to point devices at externally managed Appium servers.

Console logs use colored levels by default. File logs are archived under `logs/YYYY-MM-DD/HHMMSS/` and old date directories are cleaned automatically according to `ANDROID_AUTOMATION_LOG_RETENTION_DAYS`.

## Run

Run the ordered framework flow on every device configured in `config/appium.yaml`:

```bash
python run_tests.py
```

Run one selected device:

```bash
python run_tests.py --device emulator_5554
```

Run all configured devices concurrently explicitly; the runner auto-adds `-n <device_count> --dist=loadgroup`:

```bash
python run_tests.py --all-devices
```

Run selected devices concurrently:

```bash
python run_tests.py --device emulator_5554 --device emulator_5556
```

List configured devices:

```bash
python run_tests.py --list-devices
```

Run preflight checks only for all configured devices:

```bash
python run_tests.py --preflight --all-devices
```

If emulator sessions are flaky or slow to respond, increase `ANDROID_ADB_EXEC_TIMEOUT` and keep the default session retry settings in `.env` so transient `adb` discovery failures can recover automatically.

If you still want to run Appium manually, disable managed servers first:

```bash
set APPIUM_MANAGE_SERVERS=false
python run_tests.py --device emulator_5554
```

## Reports and artifacts

Each run writes to `reports/latest` by default, so a single execution has one stable report directory:

```text
reports/latest/
  logs/
    YYYY-MM-DD/
      HHMMSS/
        master.log
        gw0.log
        appium/
  screenshots/
  page_sources/
  metadata/
  allure-results/
  allure-results-<device>/
  allure-report/              # 单设备运行时生成
  allure-report-<device>/
```

Use `--report-dir reports/<name>` only when you intentionally want a separate report directory. Failure screenshots, page source, and session metadata are attached to Allure when available. After a multi-device run, the framework only generates one independent Allure report per device and does not keep a mixed HTML report.

## Framework architecture

The project now follows a PO-oriented layered layout while keeping the existing multi-device runner and diagnostics modules under `src/android_automation`:

```text
config/
  appium.yaml                             # global Appium and device configuration
src/android_automation/base/
  base_page.py                            # base page object methods
src/android_automation/pages/
  login_page.py                           # login page object example
  home_page.py                            # home page object example
  app_page.py                             # generic app state page object
src/android_automation/utils/
  logger.py                               # logger helper export
  adb_utils.py                            # ADB helper export
src/android_automation/
  runner.py                               # CLI orchestration, preflight, pytest and Allure report generation
  config.py                               # YAML/.env loading, device matrix validation
  appium_service.py                       # managed Appium server start/stop and health checks
  driver_factory.py                       # Appium capability construction
  runtime.py                              # shared execution context for runner and pytest
  session.py                              # Appium session creation with retry policy
  artifacts.py                            # screenshots, page source, metadata and Allure attachments
test_cases/
  conftest.py                             # pytest global entry, forwards to active fixture implementation
  test_app_lifecycle.py                   # lifecycle case entry
  test_smoke.py                           # smoke case entry
tests/
  ...                                     # existing test implementation retained for compatibility
```

This keeps product test cases focused on behavior and page objects, while the framework core owns device setup, Appium lifecycle, diagnostics, reporting, and parallel execution.

## Test order

The default ordered flow is:

1. install
2. launch
3. optional sample element check
4. uninstall

For multi-device execution, the runner uses `--dist=loadgroup` so each device's ordered flow stays on one worker while different devices run concurrently.
